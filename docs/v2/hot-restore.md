# 第二版：热回退准备

状态：**准备阶段**。基线为已发布的 `v1.1.1+26.3`，开发分支为 `dev/v2-hot-restore`，已合入单人世界 Voxy 兼容修复。已完成 26.3 的接口盘点和分阶段方案；在线回退逻辑尚未实现，正式部署仍使用 1.1。

## 目标与首个原型

保持服务器进程运行，对指定区块完成受控回退。首先在独立合成世界中处理无人、可完全卸载的一个区块，再扩展到矩形、跨区域和存在实体的情况。服务器不停进程不等于无停顿，保存、I/O 排空和客户端重载仍可能影响 tick。

沿用现有索引、内容对象、管理员权限、备份频率和零冷却默认值。玩家日常备份继续使用 `/chunkbackup create`。第二版的首个功能里程碑是只读预览，报告目标是否具备热回退条件；写入路径须单独验证。

## 已核对的 26.3 接口

依据本机安装的 26.3 游戏 JAR，通过 `javap` 核对类签名。[接口记录](api-survey-26.3.json) 保留输入 JAR SHA-256。签名存在仅证明接口形状，不证明调用后已经卸载、写空队列或清除缓存。

| 部分 | 当前证据 | 下一步需要证明 |
| --- | --- | --- |
| 地形 | `ServerChunkCache.getChunkNow`、`save(boolean)`；`ChunkMap.pendingUnloads`、私有 `processUnloads` | 无加载请求、生成任务或延迟卸载继续持有目标区块 |
| 区域存储 | `ChunkMap` 继承 `SimpleRegionStorage`，后者提供异步 `synchronize(boolean)` | Future 完成的准确含义、提交后是否仍可能有旧写入 |
| I/O | `IOWorker.pendingWrites`、`synchronize(boolean)` | 暂停新请求后排空所有相关任务，且不造成主线程等待环 |
| POI | `SectionStorage.storage`、`loadedChunks`、`pendingLoads`、`flush` | 对目标区块移除内存缓存和待加载状态的完整过程 |
| 实体 | `PersistentEntitySectionManager` 的卸载队列、`saveAll`、`isLoaded(UUID)`；`EntityStorage.flush(boolean)` | 实体退出与重载、跨边界 UUID 冲突、未加载实体记录 |
| 文件句柄 | `RegionFileStorage.regionCache`、`flush`、`close` | 在 I/O 线程上处理受影响区域的缓存句柄，避免替换后继续写旧文件 |
| 加载票据 | `TicketStorage.getTickets(long)`、`getForceLoadedChunks` | 区分玩家、传送门、强加载及其他模组票据，并判断可否卸载 |

当前没有直接可用的“回退区块并清除全部关联状态”公共接口。计划为 26.3 增加小范围适配层；其他游戏版本须重新验证。

## 执行约束

1. 同一世界内，备份、清理、校验和回退仍由同一个任务状态协调。开始写入前复查快照对象、权限、范围和磁盘空间。
2. 目标区域需无玩家并阻止重新进入；由加载票据或第三方模组持有、无法证明卸载完成的目标直接拒绝。不得擅自移除其他系统的票据。
3. 先保存当前状态并保留恢复点，再阻止新加载和新写入，完成区块、实体、POI 的卸载及 I/O 排空。
4. 修改前处理受影响 MCA/MCC 的缓存句柄。即使只选一个区块，事务也可能替换整个区域文件，因此相邻区块写入必须被协调。
5. 应用时复用离线事务的 staging、before 和持久日志思想。现有离线入口的世界锁继续保护外部工具；热路径需要单独的进程内所有权协议，不能直接对运行中的世界调用离线恢复。
6. 重载地形、实体和 POI，检查游戏内状态及客户端区块同步，再恢复进入和调度。Future 按阶段推进，不在主线程等待需要主线程回调才能完成的任务。
7. 无法证明应用前条件时终止预览或准备；写入后失败则保持区域隔离并恢复 before。若不能恢复并验证，正常停服，交由已验证的离线恢复路径处理。

仅冻结 tick 不会自动排空 I/O 或丢弃缓存。仅改磁盘文件可能被旧内存再次保存覆盖；完整性不能由“文件哈希正确”单独证明。实体 UUID 的全世界查重范围和跨区块关联仍是未解决问题，不能只凭一个 `isLoaded` 接口宣布解决。

计划状态顺序：

```text
PREVIEW -> QUIESCE -> SAVE_CURRENT -> DRAIN -> UNLOAD -> APPLY
                                                     |
APPLY -> RELOAD -> VERIFY -> RESUME                    +-> RECOVER
```

每阶段记录完成条件和超时后的恢复动作，持久写入后的中断沿用事务恢复机制。具体接口调用顺序在 M1/M2 验证后固定。

## 里程碑与验收

| 阶段 | 状态 | 可交付证据 |
| --- | --- | --- |
| M0 接口盘点与范围 | 已完成 | 可重复运行的只读接口盘点脚本、输入哈希和本方案 |
| M1 只读热回退预览 | 计划中 | 输出选择范围、加载/票据、待处理任务及拒绝原因；不修改世界 |
| M2 单个卸载区块原型 | 计划中 | 合成世界内服务器进程/PID 保持，地形/容器/实体/POI 正确，邻区块原样，重启后结果保持 |
| M3 边界与失败恢复 | 计划中 | 负坐标、跨 MCA/MCC、并发保存/请求、加载票据、实体冲突及各持久阶段中断的恢复结果 |
| M4 客户端与长期运行 | 计划中 | 真实隔离客户端重载无旧画面/实体重复，后续保存和再次启动不覆盖回退结果；耗时与负载记录 |

验收使用明确标记的合成存档，包含箱子物品、床 POI、带标记实体及正负相邻区块。对 1、4、16 个区块逐步扩大；热回退的实际上限在结果明确后决定。现有核心、单人客户端和服务端检查作为回归基线，版本和覆盖边界见 [构建与验证](../development.md#验证边界)。

当前生产服没有执行热回退、替换任何第二版 JAR，或改动客户端运行参数。下一步是 M1 的只读预览与可观测状态适配。

## 重复接口盘点

```sh
python tools/survey_hot_restore_api.py --game-jar /path/to/26.3.jar --java /path/to/java25/bin/java --output build/hot-restore-api-survey.json
```

该脚本读取类签名并生成报告，不启动游戏，也不打开世界文件。
